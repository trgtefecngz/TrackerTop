# Triage of external feedback (v0.8.2)

An external review of v0.8.2 (`4d2f258`) made 19 bug claims (A) and 10 bloat claims (B).
Each one was checked against the code, a small fixture repo or the real repo. **Nothing is
fixed here.** Failing tests for the confirmed items live on branch `triage/feedback-tests`
(`tests/feedback_triage.rs`, one test per item id; all 10 fail on v0.8.2 for the reported
reason).

How the checks were run: a debug build (`CARGO_TARGET_DIR=target/check`), the CLI
(`trackertop query …`, `install`, `review`) on fixture repos in a temp dir with
`USERPROFILE`/`HOME` pointed at a scratch folder (the real project list was never touched),
a local clone of this repo for the larger checks, and the debug UI tour
(`TRACKERTOP_UI_TOUR`) for the screenshots of A14/A15.

Severity is measured against the product rule: correct, cheap answers for AI agents; a wrong
answer is worse than none.

- **critical**: silent data loss, or a confidently wrong answer about the code.
- **high**: a wrong or empty answer on common code that the agent will act on.
- **medium**: misleading output, noise, or a broken path that is not the default one.
- **low**: cosmetic, wording, or small performance problems.

**Verdicts:** A has 17 confirmed, 2 partly true and 0 not reproducible. B has 7 confirmed,
3 partly true and 0 not reproducible. The checks also turned up 3 new findings (N1–N3).

## Recommended order of work

The edge-confidence session is changing `src/parser/rust_lang.rs`, `src/indexer.rs` and the
edges table. Batches 1–3 avoid those files and can start now. Batches 4–5 must start from
that branch after it merges.

1. **PR 1: data safety and the broken review path** (`install.rs`, `review/snapshot.rs`,
   `fsutil.rs`): A1, then N1. Tests: `a1_…` plus a new N1 test. Small and urgent: A1 destroys
   user data, and N1 breaks `review_changes` for every project-scoped install.
2. **PR 2: savings numbers the user can trust** (`context.rs`, `context/*.rs` baselines,
   `tokens.rs`, `ui/projects.rs`, `ui/savings.rs`, `registry.rs`): A7, A9, B4, B5, then A8
   (`index_totals`, background refresh). Tests: `a7_…`, `a9_…`.
3. **PR 3: agent-facing answers outside the parser** (`context/analysis.rs`,
   `context/search.rs`, `mcp.rs`, `changes.rs`): A17 (ranking), A16 (manifest diffs, doc
   mentions), A18, A12, and B6 slimming (`recall`→`resume`, drop `token_stats` from MCP,
   shorter footer). Tests: `a18_…`, plus a small task-to-file golden set for A17.
4. **PR 4, after edge-confidence: what gets indexed** (`indexer.rs`): A2, A5, N2, N3, A11,
   then A10 (incremental edges). Tests: `a2_…`, `a5_…`, `n2_…`, `a11_…`.
5. **PR 5, after edge-confidence: Rust references** (`parser/rust_lang.rs`, resolver): A3
   (filter at resolution time; label as `heuristic`), A4 (aliases, plus const/static
   references). Tests: `a3_…`, `a4_…`. Add these cases to the golden corpus.
6. **PR 6: MCP concurrency** (`mcp.rs`, `checks.rs`): A6. Independent of the others, but
   touches `mcp.rs` like PR 3, so it goes after PR 3.
7. **PR 7: UI and housekeeping**: A13, A14, A15, A19, B1, B2, B3, B9 (removals only after the
   user agrees).

The order inside the correctness group is by harm: data loss (A1) first, then wrong answers
the agent will act on (A2, N1, A3, A4, A17), then wrong numbers (A7), then noise (A16, A11,
A5).
