## Run log

### 2026-11-20 (run 1, interactive session): milestone 1
- `src/review/snapshot.rs`: the base commit is checked out into `.trackertop/review-base/<commit12>/` and indexed there.
  - The checkout uses a private `GIT_INDEX_FILE` with `read-tree` and `checkout-index`. It registers no worktree, runs no hooks, and leaves the user's branch and index alone.
  - Snapshots are published by renaming a temp dir; the newest 3 are kept.
  - Monorepo packages work: the project subtree is checked out, run from the repository top level.
- `index_snapshot` indexes without registering the snapshot in the desktop app's project list. A snapshot ignores `.gitignore` rules from above its own root, because it lives under the git-ignored `.trackertop/`, which would otherwise hide every file.
- `src/review/mod.rs`:
  - `review(root, base)` compares the working tree (commits, staged, unstaged and untracked work) with the merge base of `base` and HEAD.
  - Symbols are compared per file by (qualified name, kind), with occurrences paired in line order. Hunks touch head symbols by new range and base symbols by old range.
  - Each symbol is classified as added, removed or modified, with `file:line` on both sides. Moved-but-unchanged code is not listed.
- CLI: `trackertop review [--base <ref>] [--format md|json]`. The default base is origin/HEAD, then main, then master.
- On this repo vs `v0.6.0`: 68 modified, 298 added, 18 removed symbols (the removed ones are the old hand-written TS scanner), in about 3 s.
- Tests: integration test `review_lists_changed_symbols_for_every_kind_of_change` covers:
  - modify, add and remove, file rename, file deletion, untracked files;
  - a project in a subdirectory, and a base branch that moved on (merge base);
  - the user's git state untouched; a cached second run giving the same answer.
- Both bugs found while building it were caught by that test: parent ignore rules hid the snapshot's files, and `checkout-index` from a subdirectory wrote nothing. Totals: lib 96, integration 23. Clippy is clean in both configs.

## Notes and decisions
- `impl X` containers are reported as modified when a hunk falls between their methods. Milestone 2 should not count a container's blast radius when a child symbol already carries the change.
- Symbol renames show up as one removal plus one addition. Rename detection (same body) can come with the `broken-ref` rule.

### 2026-11-20 (run 1, continued): milestone 2, first rules
- `src/review/rules.rs`. Findings have a stable id (`rule:path:symbol`), a severity, a `file:line` location and evidence.
  - `broken-ref`: a removed symbol (not moved) whose base-graph callers still exist at head. The finding is raised only if the call text is still in the caller's current body, and that line is quoted as evidence. A qualified or free call is high severity; a `.method(` match alone is medium.
  - `impact`: a modified function with ≥ 8 code dependents within 3 hops (medium at ≥ 25), listing callers and the tests that reach it.
  - `untested`: an added or modified function that no test reaches within 3 hops. Low severity, and the message says edges are partly heuristic.
  - Dependents count only code edges (calls, tests, type uses, impls). Markdown mentions, imports and co-change history inflated every blast radius before.
  - Low findings are capped at 15 in Markdown; all are in JSON.
- Graph fixes found by dogfooding the rules (they affect every tool):
  - Calls inside macro arguments (`assert_eq!(f(x), …)`, `vec![…]`) became edges. Before, most Rust test → code edges were missing.
  - Rust method calls on values (`x.flush()`) now resolve only to methods. With no project method of that name, they get no edge.
  - Bare calls never bind to modules or doc sections: `review()` used to resolve to `pub mod review`.
  - Effect on this repo vs v0.6.0: untested findings went from 86 to 21. The 21 left are real: UI, `render_markdown`, `default_base`, `run_mcp_server`.
- Tests: fixture `review_rules_flag_broken_refs_impact_and_untested_code`, plus a macro-call unit test. Mutation check: disabling the text check of broken-ref fails the fixture. Totals: lib 98, integration 24.

### 2026-11-20 (run 1, continued): milestone 3
- `review_changes` MCP tool (`TrackerEngine::review_changes`). Findings come first, then the dismissed list, then changed symbols. A token budget cuts the symbol list first.
  - A finding is dismissed with `remember(target=<finding id>, kind=dismissed, reason)`. It is not raised again, but it is listed by id and reason, so nothing disappears silently.
- The MCP `instructions`, README tool table and CLI table mention it.
- Test `review_changes_hides_dismissed_findings_and_says_so`. Totals: lib 98, integration 25.
- Open: "resolved / new / unchanged vs the previous review". It needs the previous run's ids stored, which can be done together with note provenance (milestone 4). Re-raising a dismissed finding after its code changes also depends on milestone 4.

### 2026-11-20 (run 1, continued): milestone 4
- Notes record provenance: `commit_id` and `code_hash` columns, added in place, plus Markdown front matter.
  - The hash covers the target's code: a symbol's lines, a whole file, or for a review finding id `rule:path:symbol` that symbol (its file if the symbol is gone).
- Every place a note is shown (read_symbol, read_symbols_batch, file_outline, repo_map, recall) adds `[POSSIBLY OUTDATED …]` when the code changed since the note was written, or when the target can no longer be found.
- `review_changes`: a dismissed finding stays hidden only while its code is unchanged. After a change it is raised again, with "dismissed earlier (note #N: reason), but its code changed since: re-check".
- Notes written before v0.8 have no hash: they are shown as before, with no claim either way.
- Test `notes_are_flagged_when_their_code_changes` covers both directions (unchanged → no flag, changed → flag and re-raise). Totals: lib 98, integration 26.

### 2026-11-20 (run 1, continued): more rules
- `new-cycle`: an import or dependency cycle the change created among JS/TS/Python/Go files, with the dependency it added as evidence.
  - Medium severity for a new cycle; low when an existing cycle took in more files.
  - Rust is left out on purpose: modules of one crate depend on each other freely.
  - A cycle that existed at the base and gained no new dependency is not reported.
- `bloat`: a code file that crossed 3,500 tokens in this change.
- Graph fix: a bare Rust call `f()` no longer resolves to a method; methods need `x.f()` or `Type::f()`. Found through a false `parse_range -> CheckKind::parse` edge.
- On this repo vs v0.6.0: broken-ref 0, new-cycle 0, impact 11, bloat 5, untested 18.
- Test `review_reports_import_cycles_the_change_creates` checks that a new a↔b cycle is reported and that a pre-existing c↔d cycle is not. Totals: lib 98, integration 27.
